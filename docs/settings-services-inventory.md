> Native Windows rewrite: legacy PowerShell details below describe the preserved fallback. See [Windows agent](windows-agent.md) for the new app and stage-one limitations.

Read-only baseline for phase J, inspected on 2026-10-09 after phase A. This document lists key names and source paths only. No deployment environment, credentials, or live service configuration was read. “Restart” describes the current implementation, not the intended phase J behavior.

## Environment and compose

`NovaConfig` reads environment defaults once when instantiated (`apps/api/src/core/config/nova-config.ts:6`). Changing an environment file requires recreating the NOVA container; restarting a container alone does not reload compose environment values. No existing settings endpoint replaces the service connection environment values. Secrets have no usable default.

## Existing local settings, security and backups

`settings/store/settings.store.ts:27` stores persona, quick actions, tool overrides, skills, widgets, sidebar, helper mode/display, helper preferences and scoped standing approvals. Atomic writes use mode `0600` (`settings.store.ts:137`). These values are runtime editable through the existing settings controller, without service restarts. Skill webhook secret headers are kept server-side and public skill projections mask them.

`settings/settings.guard.ts:43` checks the boot-configured PIN on guarded routes and requires `x-nova-admin: 1` for writes. Public routes explicitly bypass it. Current protection does not implement a settings session timeout, failed-attempt throttling or persisted PIN replacement; phase J must add those deliberately.

`GET /api/settings/export` / `POST /api/settings/import` currently cover persona, quick actions, tool overrides, public skills, widgets and sidebar (`settings/settings.controller.ts:709`). They omit service connections, helper preferences/mode, standing approvals, MCP configuration, Node-RED flows, lists and model policy. Secret header names are exported but values are omitted; import reports required replacements. This is not yet the complete-system backup requested in J2.5.

The existing audit log records settings mutations without credential values. There is no general configuration revision store or rollback API. Before migration, preserve the existing settings JSON and related local stores; test that version-one skills/widgets/sidebar retain their IDs and values. A new service settings store must take precedence over environment defaults while keeping environment and compose wiring as explicit fallback/bootstrap inputs.

## Phase J implementation update (2026-10-10)

The preceding table is the phase A baseline. The new guarded `/api/settings/services` adapter surface
now manages nine connection configurations. `core/config/service-connections.ts` validates the allowlist
and applies private `services.json` overrides at bootstrap. Existing settings remain dynamically editable;
service connection changes explicitly require restarting NOVA because several integrations cache their clients.

`GET /services`, `PUT /services/:id`, `POST /services/:id/test`, `GET /services/:id/status`,
`GET /services/history`, `POST /services/history/:revision/rollback` are relative to `/api/settings`.
All require the existing settings guard; probes, changes and rollback also require its admin header.
Secrets return only presence flags and never enter history/audit arguments. Proxmox token IDs are also secret.
Environment MQTT URLs remain byte-for-byte unchanged when that connection has no overrides.

PINs now stay only in browser memory for fifteen minutes. Five incorrect supplied attempts block
that client for five minutes; missing PINs do not consume attempts. The page preserves existing data
with a local private snapshot and tests explicit-null backup defaults.

Service-specific inventory filters, live client restart, full export/import and container control remain pending.
OmniRoute endpoint changes fail closed until their gateway provenance matches the trusted deployment.

MCP status is also available in the PIN-protected settings page. NOVA-owned server enable/disable edits are
kept in `mcp-settings-history.json` with mode `0600`; the bounded history contains only server ID, time and
before/after enabled state. A rollback requires a fresh dangerous confirmation and an unchanged MCP config.
The MCP command, args and environment are not copied to history. Per-tool risk changes are recorded
with a fresh confirmed rollback path that verifies the current config and that the tool is still active.
MCP config export/import remains pending.
